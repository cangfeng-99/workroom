# WorkRoom 一期方案（对话 → 拆分 → 横向树）

版本 `P1-r2` ｜ 2026-10-23 ｜ 状态：标签页与资料库已跑通，待用户看视觉

## 1. 已定的四件事

| 决策 | 结论 | 影响 |
|---|---|---|
| 改造方式 | 推倒重来，新工程 `workroom/` | 旧 `backend/` 只作参考，数据不迁移 |
| Key 存放 | 本机加密存库 | 已用 Windows DPAPI 实现，绑定当前用户 |
| 外部接入 | 项目接口 + 访问令牌 | 三期，一期只留位置 |
| 一期范围 | 对话 → 拆分 → 横向树 | 资料库已提前做成最小版，多 AI 协同进二期 |

技术栈：**Django 5.2 + 服务端模板 + 少量原生 JS**（不引前端框架、不引 Node）。
树用绝对定位的节点 + SVG 连线，坐标由 Python 算好，浏览器不做布局计算。

## 2. 数据模型

| 模型 | 关键字段 | 说明 |
|---|---|---|
| `Project` | name、goal_title、goal_detail、goal_deadline | 目标就是树的最右端，一个项目一个目标 |
| `Member` | kind(human/ai)、name、role、provider、model_name、key_ciphertext | AI 是成员，有角色；Key 加密后存这里 |
| `Task` | parent、title、detail、assignee、start/end、status、priority、order | `parent` 为空即第一层分支；状态 待开始/进行中/已完成/受阻 |
| `ChatMessage` | role(user/assistant)、content、payload(JSON)、applied_at | assistant 的 `payload.tasks` 是拆分草案；`applied_at` 防重复写入 |
| `LibraryEntry` | kind(rule/artifact/decision)、title、body、task | 资料库：规则约束 / 产物 / 决策，可关联任务 |

一期**不做**账号与登录：本机单人，成员是数据记录。二期加账号时再加 owner 与外键，不返工现有表。

## 3. 页面结构

### 3.0 项目选择页（`/`）

- 卡片列出全部项目（最宽 1180px，卡片 ≥320px）：名称、目标、进度条与百分比、任务数、团队头像，右下角圆形「→」入口
- 点卡片进对应项目；旧书签 `/projects/…`、`/accounts/…` 一律 302 回首页
- 「＋ 新建项目」就地展开，创建后直接进入新项目

### 3.1 项目内：面包屑 + 标签页 + 检查器

```
┌──────────┬──────────────────────────────────────────────┐
│ 项目      │ 项目 / 开发项目 v1                 40% · 2/5  │
│ 团队      ├──────────────────────────────────────────────┤
│ 真人/AI   │ 对话    任务树 5    资料库 3                  │
│          ├──────────────────────────────────────────────┤
│          │ 工具条（图例 / 筛选 / 新增）                   │
│          ├────────────────────────────────┬─────────────┤
│          │ 对话 或 横向树 或 资料库表格     │ 检查器       │
└──────────┴────────────────────────────────┴─────────────┘
```

- **标签页**：对话 / 任务树 / 资料库，任务数与资料库条数显示在标签上；切换靠 `?tab=`，服务端渲染，无 JS 也能用
- **任务树**：目标在右端，任务向左分层；点节点右侧看详情、改状态
- **资料库**：表格（名称 / 类型 / 更新时间 / 关联任务），支持按类型筛选、新增条目、行内删除（悬停出现 ×，确认后删除）
- **删除项目**：左栏项目行悬停右侧出现「×」，确认后删除（与列表卡片同一入口逻辑）
- **外部工具成员**：左栏「外部工具」列出已接入的 Codex / Cursor / WorkBuddy（绿点＝配置已写入）；
  点「＋」把它加入当前项目，团队里显示为「外部 · 执行」并带 MCP 徽标。
  外部成员不参与对话和讨论（没有 API），但可以被指派任务；任务详情「改负责人」可选它。
- **删除 AI**：在左栏团队列表里，鼠标移到 AI 行右侧出现「×」，确认后移出团队
  （`is_active=False`，Key 清空）；不再出现在对话/讨论/选择器里，历史消息与任务记录保留。
  删除后停留在当前标签页（隐藏字段 next 带回当前地址）
- **接入 AI**：左栏「+ 接入 AI」，只填名称、模型商、模型与 Key；加入后它会在群里自我介绍，
  并根据项目目标和其他成员自己定角色、讨论职责与身份（`identity` 任务），之后可随时改
- **AI 身份**：左侧团队里点 AI 成员，填名称、角色、身份与职责，再配模型商/模型/Key（DPAPI 加密，不回显）。
  角色决定它被怎么分工，身份设定会写进提示词，决定它怎么想、先看什么、不做什么
- **自己定身份**：新成员接入后先跑一次 `identity` 任务，由模型根据项目和现有成员给出 role/duty/persona
  和一句自我介绍；失败则保留默认值并提示手动配置
- **团队指令**：在聊天里直接说「把 A 和 B 的身份互换」「让 A 做决策」「把 A 改名成 B」，
  服务端识别后立即执行并回一条系统提示，不调用模型
- **回答者**：对话输入框左侧选「由谁回答」，只列出已配 Key 的 AI；消息上标出是谁回的。
  选择会记住：切换时写 URL 的 `?ai=` 和 90 天 Cookie（`ai_<项目id>`），刷新、切标签页都不丢
  下拉是自绘菜单（原生 select 的弹层没法统一风格），选中后立即更新按钮文案并收起
- **讨论**：两个以上 AI 配了 Key 时，下拉多出「讨论 · N 个 AI」。选中后按成员职责分三轮：
  **提议 → 评审 → 决策**，每轮由对应职责的 AI 发言，后一轮能看到前面的记录；只讨论，不生成任务草案
- **讨论职责**：成员配置页可选 提议 / 评审 / 决策 / 执行；没有决策者时由最后一位 AI 拍板，
  只有一位 AI 时直接给结论
- **检查器**：随标签页变化——任务详情、资料库条目详情、或项目目标概览
- 窄屏（≤1020）隐藏检查器；≤860 隐藏左栏

### 3.2 视觉规范

- 浅灰绿底 `#f1f3ee`，白色工作区卡片，1px 边线 `#e7e9e1`
- 主色只用一个深绿 `#1f5b43`（选中节点、主按钮、进度条）
- 标签页用黑色下划线，不用彩色胶囊；表单控件自绘，避免原生弹层破坏风格
- 左栏顶部是「＋ 新建项目」全宽按钮；项目行、AI 行、接入按钮同宽（210px），行高 36px 左右
- 对话页不再放常驻提示条，只有未配置 AI 时才提示
- 对话气泡渲染 Markdown（标题/列表/加粗/行内代码/代码块），先转义 HTML 再解析
- 底部输入区是一张圆角输入卡：无边框多行输入在上，模型选择器在左下、圆形发送按钮在右下，
  聚焦时整卡描边发光；输入框固定高度内部滚动，不随文本变高跳动
- 克制的动效：卡片入场、hover 轻微上浮、下划线展开；尊重 `prefers-reduced-motion`
- 不用册子的米色/纸感主题

## 4. 一期闭环（已实现）

1. 新建项目（自动带「我」+「DeepSeek」两个成员）
2. 对话里说需求 → 生成拆分草案（当前是**固定演示响应**，未连模型）
3. 草案列出任务、负责人、起止日期 → 点「确认写入任务树」
4. 任务落库并出现在树里，已存在的同名任务不重复创建
5. 点节点看详情、改状态，顶部完成度跟着变
6. 资料库可新增规则/产物/决策，可按类型筛选、点行看详情

## 5. 真实模型调用（已接）

- 成员配置页：`/p/<id>/members/<id>/`，先填身份（名称/角色/身份与职责），再选模型商、填模型与 Key
- 每个 AI 的身份设定随请求一起发给模型，任务分配时参考角色；AI 回复记录所属成员
- 对话输入框左侧可选择由哪个已配 Key 的 AI 回答（不配 Key 的成员不出现）
- 每次提交都落一条 `ReplyJob`，请求立刻返回；真正的模型调用在后台线程里跑
- **流式**：群聊模式下用 `stream: true` 读 SSE，边收边写 `partial_answer` / `partial_reasoning`；
  页面每 0.7 秒轮询一次，气泡里逐字更新回答、展开「思考过程」、显示阶段/秒数/字数
- 拆任务（单 AI）输出的是 JSON，不做逐字展示，只显示「正在拆解任务」
- 「停止」把任务置为 cancelled：后台在下一个 chunk 检查到取消就断开上游连接，
  停止继续生成；即使已经返回也丢弃结果
- 「讨论」建一个任务，内部按轮顺序调用（提议 N 次 + 评审 M 次 + 决策 1 次），
  单个 AI 失败会记一条「没答上来」，不影响后续轮次；按各自 Key 计费
- 提交后立刻插入「正在思考…（谁）」气泡并把按钮置为「等待回复…」，不让页面看起来没反应
- 回复要求模型先写「判断依据：」再写「回答：」，前端拆开：判断依据进折叠块、回答进气泡
- 流式过程中，供应商推送的 `delta.reasoning_content` 实时显示在「思考过程」里并自动展开；
  没有该字段时，模型自述的「判断依据」同样实时可见
- Key 用 **Windows DPAPI** 加密（`crypto.py`，ctypes 调 CryptProtectData，零依赖、绑定当前用户），
  页面上永不回显；换 Windows 账号或机器需要重填
- 调用沿用硬规则：HTTPS 443、禁重定向、DNS 全量校验并拒绝内网地址、60 秒超时、256 KiB 上限、Key 不进日志
- 输出先过 `planner.validate`：1–15 个任务、单根、层级 ≤5、日期在项目窗口内、负责人必须是本项目成员
- 未配置 Key 时自动回落到演示拆分，并在工具条标明「演示响应 · 未连接模型」
- 失败（401/超时/JSON 不合法）写成一条 AI 消息说明原因，不写入草案

**尚未验证**：没有用真实 API Key 实连过任何供应商。测试里 `fetch_plan` 全部是 mock，
加密、表单、回落、错误路径是真实执行。第一件事是你自己配一把 Key 发一句，确认真实链路。

## 5.1 只读 Agent（L3）

- 输入框左下角新增 **Agent** 开关（按项目记 Cookie），打开后发送走 `mode=agent`。
- 循环：目标+项目上下文 → 模型每步输出一个 JSON 动作 → 本地执行只读工具 → 结果回填 → 最多 6 步 → 计划。
- 工具（`agent_tools.py`）：`list_dir`、`read_file`（≤64 KiB / 400 行）、`search`（≤20 条命中）。
- 根目录：`settings.AGENT_ROOT`，默认工作区根，可用 `WORKROOM_AGENT_ROOT` 覆盖；**只读**。
- 黑名单：`.env*`、`*.key/.pem/.sqlite3/.db`、`.git`、`node_modules`、`__pycache__`、二进制与图片；
  路径必须解析在根目录内，越界直接报错。
- 展示：执行中在等待气泡里逐行显示「1. list_dir .」；完成后消息里带「执行步骤 · N 步」可展开清单。
- **没有写文件、没有跑命令**：执行类动作留给 Codex / WorkBuddy 这类外部工具（三期接口）。

## 5.2 外部工具接入（MCP）

- `workroom/mcp_server.py`：stdio 的 MCP 服务（JSON-RPC 2.0，换行分隔），由 Codex / Cursor / WorkBuddy 直接拉起。
- 工具（10 个）：`list_projects`、`get_project`、`list_tasks`、`get_latest_plan`、`create_task`、
  `update_task_status`、`add_library_entry`、`next_task`、`claim_task`、`submit_result`。
- 交付闭环：外部工具 `submit_result` → 写对话与资料库 → 项目 AI 自动审核（REVIEW job）→ 建议下一步；
  `next_task` / `claim_task` 让它们领活与认领。
- 能力边界：只读写 WorkRoom 的项目/任务/资料；**不读代码目录、不执行命令**；执行由外部工具自己做，做完回报状态。
- 应用内 `/connect/` 页面：每行一个客户端，点「接入」由本机直接把配置写进
  `~/.cursor/mcp.json`、`~/.codex/config.toml`、`~/.workbuddy/mcp.json`（先备份，再合并，保留其他 server）；
  另有「全部接入」和手动配置兜底。
- 打包：`launcher.py` 支持 `--mcp`；冻结后一键写入的命令自动变成 `WorkRoom.exe --mcp`。
  数据目录在 `%LOCALAPPDATA%\WorkRoom`，模板/静态从 `sys._MEIPASS` 读。详见 `docs/PACKAGING.md`。
- 没有令牌：stdio 是本机进程，谁拉起谁就有权限；不要把这个脚本暴露成网络服务。
- 握手速度：Django 改为**首次调用工具时**才加载，`initialize` 立即回包（后台线程预热）；
  stdout/stdin 强制 UTF-8。否则 Windows 首次导入 Django 要 3–4 秒，客户端会报 initialize timeout。

## 8. 已知限制

| 限制 | 影响 | 处理 |
|---|---|---|
| 拆分是固定演示响应 | 不能真的理解需求 | 下一步接模型 |
| 移动端隐藏检查器 | 手机上点节点只能看到高亮 | 二期改底部抽屉 |
| 没有账号 | 换人共用一台机器没有隔离 | 四期 |
| 树是整棵渲染 | 上千节点会卡 | 先按单项目 ≤ 500 节点设计 |
| 项目不能改名/归档 | 项目多了难管理 | 二期 |
| 删除是软删除（保留历史） | 数据库里仍留记录 | 有意为之；需要彻底清除再加命令 |
| 手机端隐藏左栏，无法删除成员 | 手机上暂时不能管理团队 | 后续把删除放进移动端抽屉 |
| 真实链路没实测 | 供应商差异可能暴露 | 你配一把 Key 先试 |
| 讨论会多一次模型调用来出草案 | 比纯讨论多花一次钱 | 可接受；失败不影响讨论记录 |
| 停止在下一个 chunk 才生效 | 已生成的少量 token 仍会计费 | 单机可接受；不是硬中断 |
| 服务重启时进行中的任务会丢 | 气泡在 10 分钟后自动清掉 | 二期换成真正的队列 |

## 9. 怎么跑

```bash
cd workroom
../.venv/Scripts/python.exe manage.py migrate
../.venv/Scripts/python.exe manage.py seed_demo   # 三个演示项目，只需一次
../.venv/Scripts/python.exe manage.py runserver 127.0.0.1:8000
```

地址统一用 **http://127.0.0.1:8000/**。

注意：启动用了 `--noreload`，改模板或 Python 后要重启进程才会生效（Django 默认走缓存模板加载器）。

测试：`../.venv/Scripts/python.exe -m pytest -q`（26 项）
